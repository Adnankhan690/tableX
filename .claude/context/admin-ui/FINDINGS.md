# Admin UI audit — 127 findings

Produced by five parallel readers, each given one slice of `apps/admin` plus the 18 baseline
screenshots in `/tmp/tx-before`. Recovered from the workflow journal after the design and
synthesis phases died on a spend limit; the audit itself completed.

Severity: **broken** = visibly wrong or unusable today · **high** = costs a staff member time or
legibility during service · **medium** = weakens the product · **polish** = craft.

Totals: 8 broken, 45 high, 56 medium, 18 polish.

One finding was rejected outright: the dark circle overlapping the sign-out control in every
screenshot is Next's dev-tools badge (a `nextjs-portal` element), not this app's markup. It does
not ship. The sign-out control beneath it is still a real defect, recorded below.

## apps/admin/src/components/menu-manager.tsx

- **[broken·a11y]** Every input on this page carries `outline-none`, which in Tailwind 3 compiles to `outline: 2px solid transparent`. Because Tailwind's utilities layer outranks the `@layer base` block in globals.css, it defeats the `:focus-visible { outline: 2px solid var(--ad-accent) }` rule the theme deliberately defines. Six inputs are affected (price row, new-category, and all four ItemForm fields). The only remaining focus cue on the 80px price box is `focus:border-accent` — a 1px border going from #c0cad8 to #0b57d0. The Select trigger next to Prep time does NOT use outline-none, so the spice dropdown gets a real ring and the input beside it does not.
  - *Cost:* globals.css states in prose that this panel is 'driven at speed during service, often by keyboard on a laptop behind the counter, so focus has to stay obvious'. Tabbing across 93 price fields with a 1px tint as the only indicator means a manager cannot tell which of 93 prices they are about to overwrite — and this is the one screen where a stray keystroke silently changes money.
  - *Fix:* Drop `outline-none` from all six inputs and let the base `:focus-visible` ring apply; keep `focus:border-accent` as the resting-state affordance if wanted. If a custom ring is preferred, use `focus-visible:outline-2 focus-visible:outline-accent` explicitly rather than suppressing the global one. Add a rationale comment noting that outline-none in the utilities layer beats the base focus rule, so it must not be reintroduced.
- **[broken·a11y]** The inline price input is `px-2 py-1 text-sm` with no `min-h-tap` — roughly 30px tall. Ten other controls in this same file use `min-h-tap` (2.5rem/40px). It also uses `rounded` (4px) where every other field and button in the file uses `rounded-card` (10px), and `w-20` (80px) is arbitrary: a four-digit price with paise ('1299.00') nearly fills it.
  - *Cost:* Constraint 6 sets a 40px floor for touch targets on the 820x1180 tablet used at arm's length, and this is the most-repeated interactive control on the page — 93 of them in production. It is the one control on the screen that misses the floor, and mistapping it lands you inside a live money field rather than on the button next to it.
  - *Fix:* Give the input `min-h-tap` and `rounded-card` to match every sibling field, and set an explicit width sized to the longest realistic price (e.g. `w-24`) rather than `w-20`. Since the row is `items-center`, growing the field to 40px will not disturb the row baseline.
- **[high·cta]** The restore action is styled as destructive: `border-danger bg-danger-soft text-danger`. So the only red elements on the whole page are the two rows that are already handled (Kadai Paneer, Ras Malai in the screenshots), and the tap that puts a dish back on sale — a constructive, revenue-restoring action — looks like the dangerous one. The neutral 'Mark sold out' button, which is the state-changing action that actually removes a dish from the diner menu, is the quietest control in the row.
  - *Cost:* The eye lands on red first. On the full-page screenshot a manager scanning for work is pulled to the two items that need nothing, while the 26 rows carrying the actual availability decision read as inert chrome. It also teaches the wrong instinct: staff learn that red means 'this row is done'.
  - *Fix:* Use the danger tint for the row's sold-out *state* (a badge or the row treatment), not for the button that undoes it. Make the restore button a normal or accent-tinted control ('Back on sale' visual weight, keep the literal text 'Sold out — restore' — admin-journey.mjs asserts on that string), and let the sold-out row itself carry the red marker.
- **[high·density]** At production scale — 93 items across 14 categories — this page is roughly 8,500px tall (the 28-item screenshot is already ~2,580px). There is no search, no filter, no jump-to-category, no expand/collapse-all, and the category headers are not sticky, so once you are inside a 20-item category nothing on screen says which category you are editing. Collapsing your way past 14 sections takes 14 individual taps, and `overflow-hidden` on each `<section>` (line 257) would defeat a sticky header if one were added naively.
  - *Cost:* The dominant service-time task on this screen is 'the kitchen just ran out of X — mark it sold out', and it currently costs a scroll hunt through nine screens of near-identical rows while a diner is ordering that dish. This is the single largest cost of the page at real scale, and it is invisible in the 28-item screenshot.
  - *Fix:* Add a filter field in the PageHeader `right` slot that narrows visible rows by dish name across all categories (it is the only control that scales past 14 sections), plus a collapse-all toggle. Make each category header `sticky top-0 z-10 bg-surface` and move `overflow-hidden` off the `<section>` (round the header and last row instead) so sticky can work. Keep exactly one `[role=status]` node on the page — admin-journey.mjs calls `.innerText()` on it and a second one would trip strict mode.
- **[high·state]** Every failure on this page — a rejected price, a failed availability toggle, the food-type validation — lands in one `role="status"` paragraph pinned above `<main>`, styled `bg-accent-soft text-accent`: informational blue for errors. It never auto-clears and has no dismiss control. Worse, the price input is uncontrolled (`defaultValue`, line 308), so after a rejected edit the field keeps the bad text while `load()` refetches the old price — the row now displays a number the server does not have, and the only clue is a blue line ~8,000px up, off screen.
  - *Cost:* A manager editing row 80 gets no feedback at all at the point of interaction: no red border, no inline message, nothing moves in their viewport. They walk away believing they changed a price. Blue-for-error also means the one visual channel that could flag a real failure is spent on a colour the app uses for neutral notices.
  - *Fix:* Keep the single top-of-page `role="status"` node (the e2e depends on it) but tone it by outcome — danger tint and `role="alert"` semantics for failures, accent for confirmations — and add a dismiss button. Additionally render the failure at the row: mark the offending input `border-danger`, and on rejection reset it to the server value via a `key` bump so the field can never display a price that was not saved.
- **[high·layout]** The row is `flex ... gap-3` with `min-w-0 flex-1` on the name block and `shrink-0` on the price and button, so all slack collects in one gap. On the 1440px laptop screenshot the description ends around x=630 and the ₹ sits at x=1195 — about 565px of empty space in the middle of every row. On a 2560px monitor it is ~1,685px. There is no `max-width` anywhere in the shell or on `<main>`, no column rule, and nothing tying the two halves together.
  - *Cost:* Pairing a dish with its price requires a saccade across half the screen, 93 times, with no rule or alignment cue to guide the eye — the classic wide-table mispairing risk, and this table contains prices. Meanwhile the wide screen buys the page nothing: the dead band is not used for the spice level, prep time or status that the row is missing.
  - *Fix:* Give the row an explicit grid instead of flex — e.g. `grid grid-cols-[auto_minmax(0,1fr)_auto_auto]` with fixed track widths for the price and action columns — and cap the content column with a `max-w` on `<main>` (or a `max-w-5xl` wrapper) so the gap cannot grow without bound. The reclaimed width is the natural home for the metadata listed in the separate finding about unshown fields.
- **[high·state]** `busy` is one page-wide boolean. Any request — a single price blur, one sold-out tap — sets it, and `disabled={busy}` on line 325 dims all 93 sold-out buttons to `opacity-40` at once. There is no per-row pending indicator, so nothing identifies which item is in flight. The dimmed states also fail contrast: `text-muted` at 40% over white is 1.88:1 and `text-danger` at 40% over the sunken row is 1.99:1. The price inputs are *not* disabled during `busy`, so the disabled model is inconsistent within the same row.
  - *Cost:* The e2e waits 900ms for a toggle to settle. For that most of a second the entire board greys out and the tapped row looks exactly like the other 92, so a manager cannot tell whether their tap registered — and on a tablet the natural response is to tap again. Buttons at ~1.9:1 are not readable while dimmed, so the dimming reads as a rendering fault rather than as 'working'.
  - *Fix:* Track the pending item uid (`pendingUid`) instead of a global flag, disable and spinner only that row's button, and leave the other 92 live. Replace `disabled:opacity-40` with an explicit disabled palette (e.g. `disabled:border-line disabled:text-muted` plus `disabled:cursor-not-allowed`) so the disabled state keeps a legible contrast ratio instead of being an opacity multiply.
- **[high·a11y]** The category header is a `<button>` wrapping a `<span class="text-sm font-semibold">` — not a heading — and it carries no `aria-expanded`, so the collapse state is unannounced. The control itself is an `aria-hidden` text '+' / '−' glyph sitting ~950px from the label it belongs to, with no border, no hover treatment and no chevron, so nothing signals the bar is interactive. '+' and '−' also have different advance widths, so the right edge shifts as sections toggle. Every sibling screen (order-board, tables-manager, staff-manager, settings-form) uses real `<h2>` elements for its sections; this page has one `<h1>` and zero `<h2>`.
  - *Cost:* With 14 categories, the headings are the page's only navigation structure — and they are unreachable by screen-reader heading navigation, while the expand/collapse state is invisible to assistive tech. Sighted users get no affordance either: the screenshots show a bare dash floating at the far right of an otherwise inert-looking bar.
  - *Fix:* Wrap the label in `<h2>` and keep the `<button>` inside it (or put the button inside the h2), add `aria-expanded={!isCollapsed}` and `aria-controls` pointing at the item list, and replace the text glyph with the existing inline chevron pattern from select.tsx in a fixed-size box so the header edge does not shift. Do not adopt the siblings' `text-xs uppercase tracking-wide text-muted` micro-label style here — these headings are load-bearing navigation and need size, not caps.
- **[medium·typography]** The whole page lives in a 16px-to-12px type range: `<h1>` 'Menu' is `text-base` (16px), a category name is `text-sm font-semibold` (14px), a dish name is `text-sm font-medium` (14px), a description is `text-xs` (12px). Category names and dish names are therefore the same size, separated only by one font-weight step, and the page title is 2px larger than a dish name.
  - *Cost:* Scanning is what this page is for, and a flat scale gives the eye nothing to anchor to: on the tablet screenshot 'Main Course' and 'Dal Makhani' read as peers. At arm's length on a tablet, 14px dish names and 12px descriptions are also simply small for the primary scanning target during service.
  - *Fix:* Open the scale: category headings up to `text-base`/`text-lg` semibold, dish names to `text-[15px]`/`text-base` medium, descriptions stay 12–13px but muted. The page title can stay 16px semibold — the point is that the category rung must be visibly above the dish rung, not beside it.
- **[medium·layout]** Neither the price cluster nor the action button has a fixed width, and 'Sold out — restore' renders about 25px wider than 'Mark sold out'. In both screenshots the Kadai Paneer row's ₹ and input sit ~25px left of every other row's, so the price column visibly steps out of line wherever an item is sold out. Nothing in the row sits on a shared grid — the ₹ glyph is also outside the input (line 306), so on short prices it detaches: '₹      35.00' with roughly 30px of gap in the Breads and Rice rows.
  - *Cost:* A price column that jitters cannot be read as a column — the manager loses the ability to scan prices vertically, which is the second reason to open this page. And a currency mark floating 30px from its digits stops reading as one value.
  - *Fix:* Put the price and the action into fixed-width grid tracks (see the row-grid finding) so both columns hold their x-position regardless of state, and give both button labels the same rendered width via a fixed `w-*` on the button. Move ₹ inside the field as a prefix element flush against the digits, or right-align the label group so the symbol tracks the number.
- **[medium·colour]** A sold-out row gets `bg-surface-sunken` (#eef1f6) while the price input inside it keeps `bg-bg` (#f8fafc) — so the field is *lighter* than its row, inverting the fill relationship globals.css documents ('23 form inputs use bg-bg inside a bg-surface card, so it has to stay a shade off white or every field in the panel loses its fill'). ItemForm repeats the same inversion: `bg-bg` fields on a `bg-surface-sunken` panel (line 413). The sold-out row treatment is also a 1.13:1 step off white — visible on a monitor, marginal on a tablet at arm's length — and the dish name itself is left completely unmarked.
  - *Cost:* Depth cues reverse: the field pops out of the row instead of sinking into it, which is exactly the visual bug the token's own comment was written to prevent. And 'sold out' — the state a diner will be told about — is carried by a barely-perceptible tint plus a button label, so a manager glancing at the board can miss it.
  - *Fix:* On sunken surfaces switch the field fill to `bg-surface` so a field is always lighter-to-darker in the same direction as on a white card. Give the sold-out row a stronger, non-colour-only marker: a left border in danger, and mute/strike the dish name so the state survives a glance and a colour-blind reader.
- **[medium·a11y]** 93 buttons whose entire accessible name is 'Mark sold out', with no reference to the dish they act on — unlike the price input two nodes over, which correctly carries `aria-label={`Price of ${item.name} in rupees`}`. On top of that, `aria-pressed={!item.is_available}` is combined with a label that also changes, so a sold-out row announces 'Sold out — restore, pressed' — the pressed state and the name describe opposite things.
  - *Cost:* A screen-reader user arrowing the list hears 93 identical buttons and cannot tell which dish is about to go off the menu. The contradictory toggle semantics make the state unresolvable even when the name is fixed.
  - *Fix:* Add a visually-hidden dish name inside the button (`<span class="sr-only"> — {item.name}</span>`) so the accessible name becomes unique while the visible text stays exactly 'Mark sold out' / 'Sold out — restore' for the e2e's `has-text` selectors. Then pick one model: either a static label with `aria-pressed`, or the changing label with `aria-pressed` dropped — not both.
- **[medium·content]** The row exposes only price and availability, yet `AdminApi.updateItem` (packages/api-client/src/admin.ts:159) and `UpdateMenuItemRequest` already accept name, description, food_type, spice_level, prep_time_mins, category_uid, sort_order and status — and `updateCategory` accepts rename, status and sort_order. There is no per-row edit affordance and no per-category menu, so a typo in a dish name, a dish filed under the wrong category, or a mislabelled food type is permanent from this screen, and a category cannot be renamed, hidden or reordered at all.
  - *Cost:* Food type is the one field the code itself calls unfixable-by-guessing ('an unlabelled or mislabelled dish is simply not orderable for a large share of customers'), and the create form makes it mandatory — but once saved it can never be corrected here. The capability exists one function call away; only the UI is missing.
  - *Fix:* Add a single per-row edit control that reopens the existing ItemForm prefilled against `updateItem`, and a small control on the category header for rename/hide via `updateCategory`. Reuse ItemForm rather than a second form so the two paths cannot drift.
- **[medium·content]** The row shows food-type badge, name, description, price and the toggle — and nothing else. `spice_level`, `prep_time_mins`, `is_bestseller`, `image_url` and the item's own `status` are all present on `AdminMenuItemView` and never rendered. So the add-dish form collects spice level and prep time and they immediately become invisible, and an archived item is indistinguishable from a live one.
  - *Cost:* A manager cannot verify what they entered, cannot spot that a naan got tagged 'hot', and cannot see that an item is archived rather than merely sold out. Two of the six fields in the create form are write-only from the user's point of view — which quietly teaches staff to skip them.
  - *Fix:* Use the ~565px of reclaimed row gap for a compact metadata line: spice level, prep time, and a bestseller mark, plus a status chip when `item.status !== 'active'`. Keep it a single muted line at description weight so it does not compete with the dish name.
- **[medium·content]** A non-active category renders `{category.status}` raw — the lowercase enum string ('hidden', 'archived') — in a `bg-surface-sunken text-xs text-muted` chip, which is the same weight and colour family as the neutral '5 dishes' count sitting immediately to its left. The items inside a hidden category still render a full 'Mark sold out' button as if they were live.
  - *Cost:* A hidden category is one diners cannot see — a merchandising fact a manager needs to notice before wondering why nobody is ordering from it. Presented as a grey lowercase chip next to a grey dish count, it reads as more metadata, not as a warning. Staff also keep taking availability actions on dishes that are not on the menu at all.
  - *Fix:* Map the enum to sentence-case copy ('Hidden from diners') and give it a tint that separates it from the count — the danger or warn family, not sunken grey. Consider muting the whole section body when the category is not active so its rows visibly do not apply.
- **[medium·layout]** Both create paths are at the bottom: 'New category' is the 15th card in the stack, ~8,500px down in production, and it is visually identical to a category section — a bordered `bg-surface` card in the same `space-y-3` rhythm — so after 14 real categories you hit one that turns out to be a form. Its input is `min-w-[12rem] flex-1`, which stretches to roughly 1,000px on a 1440 laptop for a 64-character value like 'Soups'. Meanwhile `PageHeader`'s `right` slot is unused, so the full-width header bar holds nothing but the word 'Menu'. Sibling screens (tables-manager.tsx:149, staff-manager.tsx:140) use `grid gap-4 p-4 lg:grid-cols-3` with the form in a persistent column and an action in the header; this page uses `space-y-3` single-column and neither.
  - *Cost:* Adding a category at production scale requires scrolling to the end of the page, and the page's most-empty region — the header — sits directly above the content that needs an action. The absurd input width also mis-signals the expected input length. And the layout divergence from two sibling screens means the panel does not read as one product.
  - *Fix:* Move category creation behind an 'Add category' control in the `PageHeader` right slot (matching staff-manager's toggle pattern), or adopt the siblings' `lg:grid-cols-3` layout with the form in a sticky side column. Either way cap the name field at a width that matches its content (`max-w-xs`), and align the page's gap scale with the siblings' `gap-4`.
- **[medium·state]** ItemForm is a `<div>`, not a `<form>`: Enter in the name or price field does nothing, so the whole thing is mouse/tap-only to submit. The name field is not focused when the form opens. The required field (Food type) is third, behind Dish name/Price and the optional Description. And opening a draft in a second category silently replaces the in-progress one — `setDraft(emptyDraft(...))` at line 358 discards typed work with no warning.
  - *Cost:* A manager entering a batch of dishes types name, Tab, price, Enter — and nothing happens, every time. Losing a half-typed dish because you tapped the wrong category's add link is unrecoverable data loss with zero feedback. The field order also buries the one field the code treats as non-negotiable.
  - *Fix:* Make it a real `<form onSubmit>` with the save button as `type="submit"`; keep the visible text 'Add dish' (the e2e clicks it by text). Autofocus the name field on open. Promote Food type above Description so required precedes optional. Guard the category switch when `draft` has content — either keep the existing draft or confirm before discarding.
- **[medium·a11y]** Primary buttons use `disabled:opacity-40` on `bg-accent` with `text-accent-ink`. The composite is white text on ~#9dbcec: 1.94:1. This is the resting state of 'Add category' whenever the field is empty — i.e. what the screenshot shows and what a manager sees most of the time — and it is also the state of the 'Add dish' button while it reads 'Saving…' (line 506), making the progress feedback the least legible text on the screen.
  - *Cost:* 1.94:1 is below even the 3:1 large-text floor; the label is effectively unreadable, so the disabled button reads as a rendering fault rather than as 'fill the field first'. Making the in-flight confirmation the hardest thing to read is the exact inverse of what a save state should do.
  - *Fix:* Replace the opacity multiply with an explicit disabled palette — a sunken fill with muted ink that still clears 4.5:1 — and keep the enabled accent for the active state. For the saving state, keep the button's enabled colours and add a Spinner beside the label instead of dimming it.
- **[medium·responsive]** At 820px portrait the content column is 596px and the card interior 564px. The fixed right-hand cluster consumes ~205px of that (94px price group + 111px button) — 36% of the row — leaving ~278px for name and description. The tablet screenshot shows the result: 'Cottage cheese marinated in yoghurt and spice…', 'Black lentils, slow-cooked overnight with butter…', 'Bell peppers, onion, freshly ground kadai …'. `truncate` clips with no `title` attribute and no expand, so the text is unrecoverable on the device it was clipped on.
  - *Cost:* The same page is 36% dead gap on the laptop and clipped on the tablet — the layout is tuned for neither. And the truncated string is the copy diners actually read, so the manager cannot proofread on the tablet they entered it on.
  - *Fix:* With the row on a grid, let the description wrap to a second line at tablet width instead of truncating (`line-clamp-2` rather than `truncate`), and add `title={item.description}` as a cheap recovery on the laptop. Shrinking the action column (icon-plus-label, or a shorter label at narrow widths) buys back most of the 205px.
- **[medium·cta]** '+ Add a dish to {category.name}' repeats the heading printed directly above it, 14 times per page. It is also the only accent-coloured element inside each card, rendered as full-bleed left-aligned text with a literal '+' character and no border or background — so it reads as a link rather than a control while out-competing the 93 rows it belongs to. In an empty category it sits immediately under 'No dishes in this category.' (line 340), so two consecutive rows say the same thing.
  - *Cost:* 14 blue bars are the strongest repeated signal on a page whose actual work is in the rows, so the hierarchy points at the least frequent action. The context repetition also makes each label longer than it needs to be at tablet width, where horizontal room is already scarce.
  - *Fix:* Style it as a quiet secondary button (bordered, `min-h-tap`) rather than accent text so it sits below the rows in visual weight, and drop the literal '+' in favour of an inline icon. The e2e selects `button:has-text("+ Add a dish to")`, so that prefix must survive any copy change — shorten by dropping the interpolated category name only, or update the selector in the same commit.
- **[medium·state]** `EmptyState` and `ErrorState` render bare inside `<main class="space-y-3 p-4">` with no card wrapper, while every other block on the page is a bordered `bg-surface` card — so both states float unframed on the page ground. The empty state passes no `action` even though the component exposes the slot for exactly 'the one thing to do next', and its copy ('Add one to start building the menu') is also shown to read-only floor staff, who have no add control at all because `canEdit` gates the form.
  - *Cost:* These are the two states a manager sees on their worst day, and they look unfinished next to the populated page. Telling a waiter to add a category they cannot add is a dead end — and the actual form, when the viewer can use it, is in a separate card below with nothing linking the instruction to the control.
  - *Fix:* Wrap both in the same `rounded-card border border-line bg-surface` shell the categories use so the page keeps one frame vocabulary. Pass the add-category control into `EmptyState`'s `action` slot when `canEdit`, and swap the description to a read-only variant otherwise (matching the header subtitle's existing 'ask an owner or manager' wording).
- **[polish·content]** The Description field has no `maxLength`, while its siblings cap at 128 (dish name) and 64 (category name), and it is a single-line `<input>` for copy that renders as prose on the diner menu. Combined with the row's `truncate`, an over-long description is invisible on this screen after saving. The form's optionality convention is also mixed: three labels spell out '(optional)' while the required field is marked with a bare red asterisk and no legend.
  - *Cost:* Nothing on this screen tells a manager how long a description may be or shows them when they have exceeded what the row can display, so the failure surfaces on the diner's phone. The asterisk-plus-'(optional)' mix means neither convention is reliable — a manager has to read every label to know what is required.
  - *Fix:* Cap the description (a `maxLength` matching the backend's column) and show a character counter, or switch to a `<textarea>` so the entered text is visible in full. Pick one optionality convention: mark only the required field, or only the optional ones. Keep the visible strings 'Dish name', 'Food type' and the '249.50' placeholder — the e2e selects on all three.
- **[polish·state]** `collapsed` is component-local `useState`, so navigating to Orders and back re-expands all 14 categories. There is also no collapse-all control, and every sold-out tap and price commit calls `load()` — a full 93-item menu refetch — discarding the updated item that `setAvailability`/`updateItem` already returned (packages/api-client/src/admin.ts:159,173).
  - *Cost:* Any triage arrangement a manager builds (collapse the 12 categories you are not working on) is destroyed by a single navigation, so nobody builds one. And re-downloading the whole menu per tap is why the toggle takes the ~900ms the e2e waits for, during which the board is dimmed and gives no feedback.
  - *Fix:* Persist collapse state per category uid in `localStorage` keyed to the restaurant, and add a collapse-all/expand-all control next to the filter field. Apply the returned item into local state optimistically instead of refetching, keeping `load()` as the reconciliation path on error.
- **[polish·a11y]** `FoodTypeBadge` is rendered at `size={14}` with `withLabel` off. All three variants — veg, non-veg, egg — draw the identical square-with-centred-dot geometry, so at 14px the only difference between them is hue (green / red / amber). The component's own doc comment states that 'Colour is never the sole carrier of the distinction… `withLabel` puts the word on screen, because green-against-red is precisely the pair a red-green colour-blind diner cannot separate (WCAG 1.4.1)'.
  - *Cost:* This admin list opts out of the exact safeguard the primitive documents. A red-green colour-blind manager scanning 93 rows cannot separate Paneer Tikka from Chicken Tikka without hovering each badge for its `<title>` — and food type is the field the codebase itself calls the difference between orderable and not.
  - *Fix:* Fixable entirely admin-side without touching packages/ui: bump the badge size so the hue difference is at least readable at arm's length, and surface the word — either `withLabel` on the row (the reclaimed row gap has room) or as part of the metadata line proposed above. `data-food-type` and `data-tone` are emitted by the component either way, so the e2e attribute selectors are unaffected.

## apps/admin/src/components/order-detail.tsx

- **[high·layout]** The item price and the totals below it do not share a right edge. In 07-order-detail.png the item's ₹560.00 ends ~110px left of the Subtotal ₹560.00 directly beneath it, because the `Remove` link occupies the same flex row and eats the right edge. `items-start` also makes the 12px Remove text sit ~3px above the 14px price baseline, so the two collide visually while being on no shared line.
  - *Cost:* This is a bill. Staff read amounts down a column and check that the lines add up to the total they are about to collect; with the item column floating left of the totals column, every multi-line order has to be added up by eye against a moving right margin. `Money` already ships tabular-nums specifically so amounts scan down a column, and the layout throws that away.
  - *Fix:* Give the row explicit columns instead of a free flex: an amount cell with a fixed `min-w` and `text-right` that lines up with the totals block's right edge, and a separate trailing action cell of a fixed width (reserved even when Remove is absent, so paid/closed orders keep the same grid). Switch the row to `items-baseline` so price, name and action share one baseline.
